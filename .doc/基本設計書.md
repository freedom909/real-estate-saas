基 本 設 計 書

01_基本方針
1.	目的
      本基本設計書は、Minshuku SaaS の要件定義に基づき、システムを実現するための基本的な設計方針を定めるものである。
      本章では、システム全体の構成、業務・機能の分割、認証・認可、テナント、データ、API、画面、外部連携、セキュリティ、運用・監査に関する基本的な考え方を定義する。
      詳細なクラス構成、インターフェース、データアクセス処理、具体的な実装方法については、詳細設計および実装工程で定義する。
   
2.	基本設計の原則
________________________________________
2.1	要件と設計の分離
要件定義で定めた「何を実現するか」と、基本設計で定める「どのように実現するか」を明確に分離する。

要件定義
  ↓
WHAT
  ↓
基本設計
  ↓
HOW
  ↓
詳細設計
  ↓
HOW EXACTLY

要件定義で定めていない事項について、基本設計で過度に業務要件を追加しない。


2.2	責務分離
システムは、認証、ユーザー、テナント、Listing、Booking、管理、監査等の業務領域ごとに責務を分離する。

各領域は、自身が担当する業務責務を明確にし、他領域への不要な依存を避ける。
________________________________________
2.3 業務中心設計
システム構造は、単なる画面やデータベースの構造ではなく、実際の業務責務を中心として設計する。

User
Tenant
Listing
Booking
Membership
Administration
Audit
これらの業務領域を基本的な設計単位として扱う。

________________________________________
2.4 認証と認可の分離
認証（Authentication）と認可（Authorization）を明確に分離する。
Authentication
    ↓
「誰なのか」
    ↓
Authorization
    ↓
「何をしてよいのか」

認証によって利用者の本人性を確認し、認可によって対象業務・対象リソースに対する操作可否を判断する。

________________________________________
2.5 Global Role と Membership Role の分離
利用者のシステム全体における役割と、Tenant 内における役割を分離する。

Global Role
    ├─ GUEST
    ├─ CUSTOMER
    ├─ ADMIN
    └─ SUPER_ADMIN

Membership Role
    ├─ STAFF
    ├─ MODERATOR
    ├─ HOST
    ├─ AGENT
    └─ OWNER
Global Role はシステム全体における利用者の立場を表し、Membership Role は特定 Tenant における利用者の業務上の役割を表す。
________________________________________
2.6 Scope と Ownership の分離
権限制御において、単純な Role だけで操作可否を判断しない。
基本的に以下の情報を組み合わせて認可を判断する。

Global Role
+
Membership Role
+
Tenant Scope
+
Resource Scope
+
Ownership
+
Action
これにより、
「誰が」
だけではなく、
「どの Tenant で」「どの Resource に対して」「何をするのか」
を考慮した認可を実現する。

________________________________________
2.7 Tenant を基本的な業務境界とする

Tenant は、複数の利用者・業務データを管理する基本的な業務単位として扱う。
Tenant 内の利用者については Membership により所属と業務上の役割を管理する。
Tenant
 ├─ Membership
 │    ├─ User A / HOST
 │    ├─ User B / STAFF
 │    └─ User C / OWNER
 │
 ├─ Listing
 └─ Booking
また、現在操作対象となっている Tenant を activeTenant として扱い、Tenant Scope を明確にする。
________________________________________
2.8 Resource Ownership を考慮する

Tenant 内の Resource について、所有者・管理責任者が存在する場合は Ownership を考慮する。
例えば Listing について、
Tenant
   ↓
Listing
   ↓
Owner
という業務上の関係を基本設計上の考え方として保持する。
したがって、同じ Tenant に所属していることだけを理由として、すべての Resource を自由に操作できる設計にはしない。
2.9 業務ルールをシステム設計へ反映する
要件定義で定めた業務ルールを、システムの認可・業務処理・データ制御等に反映する。
例えば、
 HOST は Listing を管理できるが、Booking の確認権限を持たない。
という業務ルールがある場合、単純な「HOST だから許可」という設計にはしない。
________________________________________
2.10 拡張性

将来的な機能追加、Role の追加、Tenant 機能の拡張、外部サービス連携の追加等を考慮し、特定の機能や役割に過度に依存しない構造とする。
特に Authorization については、現在の Role 数だけを前提とした固定的な設計を避ける。
________________________________________
2.11 セキュリティを基本設計の前提とする

Security は追加機能ではなく、システム設計全体の基本条件として扱う。
特に以下を重視する。
•	Authentication 
•	Authorization 
•	Tenant isolation 
•	Resource ownership protection 
•	Sensitive data protection 
•	Auditability
•	Session / Token security 
________________________________________
2.12 API と業務ロジックの責務分離

API 層は、外部からのリクエストを受け付け、適切な業務処理へ接続する責務を持つ。
業務ルールや認可判断を API 層だけに集中させず、業務ロジックと責務を適切に分離する。
________________________________________
3.	設計の優先順位

基本設計では、以下の優先順位を基本とする。
① 業務要件への適合
        ↓
② Security / Authorization
        ↓
③ 業務責務・境界の明確化
        ↓
④ 保守性
        ↓
⑤ 拡張性
        ↓
⑥ 性能・最適化
つまり、「技術的に面白い構造」より「業務要件を正しく、安全に実現できる構造」を優先する。
これを基本方針とする。

# 02_システム全体構成

## 1. 目的

本章では、Minshuku SaaS を構成する主要な業務領域とシステム境界、および各領域間の基本的な関係を定義する。

本設計では、業務責務を明確に分離し、各業務領域が独立して拡張・保守できる構成を基本とする。

---

## 2. システム全体像

Minshuku SaaS は、宿泊施設の登録・管理、宿泊予約、利用者管理、Tenant 管理、システム管理、監査等を統合的に提供するシステムとする。

全体構成は、以下の業務領域を中心に構成する。

```text
                         ┌─────────────────────┐
                         │      Frontend       │
                         │    Web Application  │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │    API / Gateway    │
                         │   System Entry Point│
                         └──────────┬──────────┘
                                    │
             ┌──────────────────────┼──────────────────────┐
             │                      │                      │
             ▼                      ▼                      ▼
        ┌─────────┐            ┌─────────┐            ┌─────────┐
        │ Identity│            │ Business│            │  Admin  │
        │ / User  │            │ Domains │            │         │
        └─────────┘            └────┬────┘            └─────────┘
                                    │
                     ┌──────────────┼──────────────┐
                     │              │              │
                     ▼              ▼              ▼
                 Tenant         Listing         Booking
                     │              │              │
                     └──────────────┼──────────────┘
                                    │
                                    ▼
                              ┌──────────┐
                              │  Audit   │
                              └──────────┘
```

---

## 3. 主要業務領域

本システムでは、以下を主要な業務領域とする。

| 業務領域           | 主な責務                  |
| -------------- | --------------------- |
| Authentication | 利用者の認証・セッション管理        |
| User           | 利用者情報の管理              |
| Tenant         | Tenant・Membership の管理 |
| Listing        | 宿泊施設・掲載情報の管理          |
| Booking        | 宿泊予約の管理               |
| Admin          | システム管理業務              |
| Audit          | 重要操作・管理操作の記録          |
| Location       | 地域・住所情報の管理            |
| Amenity        | 設備・アメニティ情報の管理         |
| Calendar       | 予約可能日・カレンダー関連管理       |
| Payment        | 決済関連管理                |
| Review         | レビュー管理                |

ここで重要なのは、以下の設計上の区別である。

> **業務領域と技術的なデプロイ単位は同一ではない。**

すなわち、

> **業務境界 ≠ 技術的デプロイ境界**

である。

本基本設計では、業務責任を基準として業務領域を定義し、現在の Subgraph 構成に設計を拘束されないものとする。

---

## 4. Client / API / Business の基本関係

システムは、以下のようなレイヤ構成を基本とする。

```text
User
  ↓
Frontend
  ↓
API / Gateway
  ↓
Business Domain
  ↓
Data / External Service
```

Frontend は、各業務領域の内部実装に直接依存しない。

API / Gateway は、システムへの入口として機能し、必要に応じて各業務領域へのアクセスを調整する。

Business Domain は、それぞれの業務ルールおよび業務処理を担当する。

データアクセスおよび外部システムへのアクセスは、対応する Infrastructure 層が担当する。

---

## 5. Business Domain の基本境界

各 Business Domain は、業務上の責任を基準として分離する。

### 5.1 Authentication

Authentication は、利用者の本人確認および認証状態の管理を担当する。

主な責務：

* Login
* Logout
* OAuth Authentication
* Token / Session 関連処理

Authentication が回答するのは、

> **「この利用者は誰か？」**

という問いである。

一方、

> **「この利用者は何をしてよいか？」**

という判断は Authorization の責務とする。

---

### 5.2 User

User は、システムにおける利用者主体を管理する。

主な責務：

* User Profile
* User 基本情報
* User 状態

---

### 5.3 Tenant

Tenant は、利用者と業務組織との所属関係を管理する。

主な責務：

* Tenant
* Membership
* Tenant 内の役割
* Tenant 所属関係

Tenant は、

> **「この利用者は、どの Tenant に所属しているか？」**

という関係を管理する。

---

### 5.4 Listing

Listing は、宿泊施設および掲載情報を管理する。

主な責務：

* 宿泊施設情報
* Listing
* Listing 管理
* Listing 公開
* Listing 画像
* Listing 関連属性

---

### 5.5 Booking

Booking は、宿泊予約に関する業務を管理する。

主な責務：

* Reservation
* Booking Lifecycle
* Booking 状態
* Booking と Listing / User の業務関係

---

### 5.6 Admin

Admin は、プラットフォーム全体の管理業務を担当する。

主な責務：

* Platform Administration
* User Administration
* System Management
* Administrative Operations

---

### 5.7 Audit

Audit は、重要な操作および管理操作の記録を担当する。

主な責務：

* 重要操作の記録
* 管理操作の記録
* セキュリティ関連操作の記録
* 操作履歴の追跡

Audit は通常の業務処理そのものに参加することを目的とせず、

> **「何が発生したかを記録する」**

ことを目的とする。

---

## 6. Authentication と Authorization

システム全体では、Authentication と Authorization を明確に分離する。

```text
Authentication
      ↓
Who?
      ↓
User Identity
      ↓
Authorization
      ↓
What can this user do?
```

Authorization は、単一の User Role のみに依存せず、以下の情報を組み合わせて判断する。

```text
Global Role
+
Membership Role
+
Tenant Scope
+
Resource Scope
+
Ownership
+
Action
```

Authorization の具体的な基本設計については、

> **02-04 認証・認可基本設計**

で定義する。

本章では、システム全体構成上の関係のみを定義し、詳細な認可ルールは扱わない。

---

## 7. Tenant を中心とした業務関係

Tenant は、複数の利用者が所属する業務組織の基本単位とする。

基本的な関係は以下のとおりである。

```text
                 Tenant
                   │
          ┌────────┴────────┐
          │                 │
     Membership          Business Data
          │                 │
          │          ┌──────┼──────┐
          │          │      │      │
        User      Listing Booking  ...
```

1 人の User は、1 つまたは複数の Tenant に所属できるものとする。

Membership は、以下の関係を表す。

```text
User
 +
Tenant
 +
Membership Role
```

したがって、

> **Membership は User Role と同一ではない。**

この区別は、Global Role と Membership Role を分離する基本設計の重要な前提となる。

---

## 8. Resource と Ownership

業務リソースには、Owner または管理責任者が設定される場合がある。

例えば、Listing と Owner の関係は以下のように表現できる。

```text
Tenant
   │
   └── Listing
          │
          └── Owner
```

したがって、Resource のアクセス制御では Role だけではなく、以下の情報も考慮する。

```text
Tenant
+
Resource
+
Ownership
```

例えば、

> HOST は、自身が担当する Listing を管理できる。

一方で、

> HOST であることだけを理由として、システム上のすべての Listing を管理できるわけではない。

具体的な認可ルールについては、Authorization 基本設計で定義する。

## 10. システム構成の基本原則

本システムでは、以下の構成原則を採用する。

### 10.1 Domain Responsibility

業務領域は、業務上の責任を基準として分割する。

### 10.2 Loose Coupling

業務領域間の不要な強結合を避ける。

### 10.3 Clear Boundary

User、Tenant、Listing、Booking、Admin 等の業務境界を明確にする。

### 10.4 Security by Design

Authentication、Authorization、Tenant 分離、Ownership 制御をシステム全体の基本前提とする。

### 10.5 Extensibility

将来的な業務領域および機能の追加・拡張を考慮する。

### 10.6 Independent Evolution

各業務領域が、他の業務領域の業務ルールへ不要な影響を与えることなく、独立して進化できる構成を目指す。

この考え方は、特に今後の Authorization 設計において重要となる。

## 03_業務・機能構成

### 1. 目的

本章では、要件定義で定めた業務要件および機能要件に基づき、Minshuku SaaS の業務領域と主要機能の構成を定義する。

本設計では、業務上の責務を明確にするため、関連する業務・機能を一定のドメイン単位に分類する。

各ドメインの詳細なクラス構成、インターフェース、ユースケース実装、データモデル等については、詳細設計で定義する。

---

## 2. 業務・機能の基本構成

Minshuku SaaS は、以下の主要業務領域から構成する。

```text
Minshuku SaaS
│
├─ Authentication
├─ User
├─ Tenant / Membership
├─ Listing
├─ Booking
├─ Review
├─ Payment
├─ Location
├─ Amenity
├─ Calendar
├─ Administration
└─ Audit
```

各業務領域は、それぞれの業務責務を担当し、必要に応じて他の業務領域と連携する。

---

## 3. 業務領域と主要機能

### 3.1 Authentication

#### 業務目的

利用者の本人確認およびシステムへの安全なアクセスを提供する。

#### 主要機能

* OAuth ログイン
* ログアウト
* アクセストークン管理
* リフレッシュトークン管理
* 認証状態の確認
* 認証情報の検証

#### 基本方針

Authentication は「利用者が誰であるか」を確認する責務を持つ。

Authentication 自体は、利用者がどの業務操作を実行できるかという認可判断を担当しない。

---

### 3.2 User

#### 業務目的

システム利用者の基本情報を管理する。

#### 主要機能

* User 登録
* User 情報取得
* User Profile 管理
* Avatar 管理
* User 状態管理

#### 基本方針

User はシステム上の利用者主体を表す。

認証情報と業務上の所属・役割は、User Profile および Tenant / Membership の責務と適切に分離する。

---

### 3.3 Tenant / Membership

#### 業務目的

宿泊事業者等の業務単位と、その所属利用者を管理する。

#### 主要機能

* Tenant 管理
* Membership 管理
* Tenant への User 所属管理
* Membership Role 管理
* Active Tenant の切替
* Tenant 内の利用者管理

#### 基本関係

```text
Tenant
  │
  └── Membership
        │
        ├── User A / STAFF
        ├── User B / HOST
        └── User C / OWNER
```

Membership は以下の関係を表す。

```text
User
+
Tenant
+
Membership Role
```

#### 基本方針

Global Role と Membership Role を分離する。

Global Role はシステム全体における利用者の立場を表し、Membership Role は特定 Tenant 内における業務上の役割を表す。

---

### 3.4 Listing

#### 業務目的

宿泊施設および宿泊プラン等の掲載情報を管理する。

#### 主要機能

* Listing 登録
* Listing 編集
* Listing 削除
* Listing 公開
* Listing 非公開
* Listing 検索
* Listing 詳細表示
* Listing 画像管理
* Category 管理
* Amenity との関連付け
* Location との関連付け

#### 基本業務関係

```text
Tenant
```

# 04_認証・認可基本設計

## 1. 目的

本章では、Minshuku SaaS における Authentication（認証）および Authorization（認可）の基本設計を定義する。

Authentication と Authorization を明確に分離し、利用者の本人確認、利用者の所属、役割、Tenant Scope、Resource Scope、Ownership 等を適切に組み合わせて、各業務操作の可否を判断できる構成とする。

本章では、認証・認可に関する基本的な考え方および責務を定義する。

具体的な Class、Interface、Repository、Policy 実装等の詳細については、03_詳細設計で定義する。

---

# 2. 認証基本設計

## 2.1 認証の目的

Authentication は、システムを利用している利用者の Identity を確認することを目的とする。

Authentication の基本的な責務は、

> **「この利用者は誰か？」**

を確認することである。

Authentication は、利用者がどの操作を実行できるかを判断する責務を持たない。

---

## 2.2 認証方式

本システムでは、以下の認証方式を基本とする。

* OAuth Authentication
* Access Token による認証状態の維持
* Refresh Token による Access Token の更新
* Logout による認証状態の終了

OAuth Provider として、必要に応じて以下の外部認証サービスを利用できる構成とする。

* Google
* GitHub
* Facebook
* その他の OAuth Provider

---

## 2.3 認証フロー

基本的な認証フローは以下のとおりとする。

```text
User
  ↓
Frontend
  ↓
OAuth Provider
  ↓
OAuth Credential
  ↓
Authentication
  ↓
User Identity
  ↓
Access Token / Refresh Token
```

認証成功後、システムは利用者を一意に識別できる Identity を生成または取得する。

---

## 2.4 User Identity

Authentication によって確定した利用者は、User Identity としてシステム内部で扱う。

User Identity は、少なくとも以下の情報を識別できるものとする。

```text
User ID
Provider
Provider User ID
```

必要に応じて、以下の情報を保持する。

```text
Email
Name
Avatar
Email Verification Status
Issuer
Subject
```

ただし、認証情報と業務上の利用者情報は責務を分離する。

---

## 2.5 Token

認証成功後、システムは Access Token を発行する。

Access Token は API リクエストにおける利用者の認証状態を示すために使用する。

Refresh Token は Access Token の更新に使用する。

基本的な関係は以下のとおりとする。

```text
Access Token
    ↓
API Request
    ↓
Authentication
    ↓
User Identity
```

---

## 2.6 Logout

Logout は、利用者の認証状態を終了させるために使用する。

Logout 後は、対象となる認証情報を利用した API アクセスが継続して有効にならないようにする。

Token の無効化、Session 管理等の具体的な方式については、Security 基本設計および詳細設計で定義する。

---

# 3. 認証と認可の責務分離

Authentication と Authorization は、明確に分離する。

```text
Authentication
      ↓
User Identity
      ↓
Authorization
      ↓
Access Decision
```

Authentication は、

> **「誰であるか」**

を確認する。

Authorization は、

> **「何をしてよいか」**

を判断する。

したがって、認証に成功したことだけを理由として業務操作を許可してはならない。

---

# 4. 認可基本設計

## 4.1 認可の目的

Authorization は、認証済みの利用者が、特定の業務操作を実行する権限を持っているかを判断する。

認可判断では、単一の Role だけではなく、以下の情報を組み合わせる。

```text
Global Role
+
Membership Role
+
Tenant Scope
+
Resource Scope
+
Ownership
+
Action
```

これにより、

> **「誰が」**

だけではなく、

> **「どの Tenant において」**

> **「どの Resource に対して」**

> **「どの操作を実行するのか」**

を考慮した認可を実現する。

---

# 5. Global Role

Global Role は、プラットフォーム全体における利用者の基本的な立場を表す。

本システムでは、以下の Global Role を基本とする。

```text
GUEST
CUSTOMER
ADMIN
SUPER_ADMIN
```

Global Role は、Tenant に依存しない利用者全体の属性として扱う。

---

## 5.1 GUEST

GUEST は、認証されていない利用者、または限定された公開機能のみを利用する利用者を表す。

主に公開情報の閲覧等を想定する。

---

## 5.2 CUSTOMER

CUSTOMER は、宿泊サービスを利用する一般利用者を表す。

主な利用範囲：

* Listing 閲覧
* Booking 作成
* 自身の Booking 閲覧
* 自身の Booking に対する許可された操作
* Review 等の利用者向け機能

具体的な操作権限は Action 単位で定義する。

---

## 5.3 ADMIN

ADMIN は、プラットフォーム管理業務を担当する利用者を表す。

主な対象：

* User Administration
* Tenant Administration
* System Administration
* 管理対象データの管理
* Administrative Operations

ADMIN の権限範囲は、Platform Scope を基本とする。

---

## 5.4 SUPER_ADMIN

SUPER_ADMIN は、プラットフォーム全体に対する最上位の管理権限を持つ利用者を表す。

SUPER_ADMIN は、通常の Tenant Scope に限定されず、Platform Scope においてシステム全体を管理できるものとする。

ただし、具体的な操作については Action 単位で明示的に定義する。

---

# 6. Membership Role

Membership Role は、利用者が特定の Tenant においてどのような業務上の役割を持つかを表す。

本システムでは、以下の Membership Role を基本とする。

```text
STAFF
MODERATOR
HOST
AGENT
OWNER
```

Membership は、以下の関係によって表現される。

```text
User
 +
Tenant
 +
Membership Role
```

したがって、

> **Global Role と Membership Role は別の概念として扱う。**

Global Role はプラットフォーム全体における利用者の立場を表し、Membership Role は特定 Tenant における業務上の役割を表す。

---

## 6.1 STAFF

STAFF は、Tenant 内の日常的な業務を担当する利用者を表す。

---

## 6.2 MODERATOR

MODERATOR は、Tenant 内のコンテンツや業務データの確認・管理等を担当する利用者を表す。

---

## 6.3 HOST

HOST は、宿泊施設および Listing 等の運営を担当する利用者を表す。

主な業務対象：

* Listing 作成
* Listing 更新
* Listing 管理
* Listing 公開
* 自身が担当する業務リソースの管理

---

## 6.4 AGENT

AGENT は、Tenant 内において所有者または運営主体を支援する業務担当者を表す。

具体的な操作範囲は Action および Resource Scope によって定義する。

---

## 6.5 OWNER

OWNER は、Tenant における事業主体または管理責任者を表す。

Tenant 内の重要な業務管理について、必要な権限を持つものとする。

---

# 7. Tenant Scope

Tenant Scope は、認可判断を行う際の業務組織上の範囲を表す。

基本的には、利用者が現在どの Tenant の業務を操作しているかを明確にする。

```text
User
  ↓
Active Tenant
  ↓
Membership
  ↓
Membership Role
  ↓
Business Operation
```

Active Tenant ID は、

> **認可権限そのものではなく、現在の業務スコープを示す情報**

として扱う。

---

## 7.1 Platform Scope

Platform Scope は、Tenant 全体を横断したプラットフォーム管理範囲を表す。

主に以下を対象とする。

```text
ADMIN
SUPER_ADMIN
```

ただし、ADMIN と SUPER_ADMIN の具体的な操作権限は Action 単位で定義する。

---

## 7.2 Tenant Scope

Tenant Scope は、特定 Tenant 内の業務範囲を表す。

Tenant Scope で業務操作を行う場合、原則として対象 Tenant に対する Membership が必要となる。

```text
User
  +
Tenant
  +
Membership
  +
Membership Role
```

---

# 8. Resource Scope

Resource Scope は、認可対象となる具体的な業務リソースの範囲を表す。

例えば Listing の場合、

```text
Tenant
   │
   └── Listing
```

という関係を持つ。

Booking の場合は、

```text
Tenant
   │
   └── Booking
          │
          ├── User
          └── Listing
```

のような業務関係を持つ。

したがって、認可判断では対象 Resource がどの Tenant に属しているかを確認する。

---

# 9. Ownership

Ownership は、特定 Resource に対する所有または管理責任を表す。

例えば Listing について、

```text
Tenant
   │
   └── Listing
          │
          └── Owner
```

という関係を持つ。

そのため、同じ Membership Role を持つ利用者であっても、対象 Resource の Ownership によって許可される操作が異なる場合がある。

例えば、

```text
HOST
  +
Tenant Membership
  +
Listing Ownership
```

を満たす利用者に対して、自身が担当する Listing の更新を許可する、といった認可ルールを定義できる。

---

# 10. Action

Authorization では、最終的に「何を実行しようとしているか」を Action として明示する。

代表的な Action は以下のとおりとする。

### Listing

```text
LISTING_CREATE
LISTING_READ
LISTING_UPDATE
LISTING_DELETE
LISTING_PUBLISH
```

### Booking

```text
BOOKING_CREATE
BOOKING_READ
BOOKING_CONFIRM
BOOKING_CANCEL
```

### Membership

```text
MEMBERSHIP_READ
MEMBERSHIP_INVITE
MEMBERSHIP_UPDATE
MEMBERSHIP_REMOVE
```

必要に応じて、今後の業務拡張に合わせて Action を追加する。

---

# 11. 認可判断モデル

本システムでは、以下の情報を組み合わせて認可を判断する。

```text
Subject
   +
Global Role
   +
Membership
   +
Membership Role
   +
Scope
   +
Resource
   +
Ownership
   +
Action
   ↓
Authorization Decision
   ↓
ALLOW / DENY
```

概念的には、以下のように整理する。

```text
Global Role
        +
Tenant Membership
        +
Membership Role
        +
Tenant Scope
        +
Resource Scope
        +
Ownership
        +
Action
        ↓
ALLOW / DENY
```

これにより、単純な Role-based Access Control だけではなく、Tenant および Resource の関係を考慮した認可を実現する。

---

# 12. 認可判断の基本フロー

認可処理は、以下の流れを基本とする。

```text
Request
   ↓
Authentication
   ↓
User Identity
   ↓
Active Tenant / Scope
   ↓
Membership
   ↓
Resource
   ↓
Ownership
   ↓
Action
   ↓
Authorization Decision
   ↓
ALLOW / DENY
```

認可判断に必要な情報を取得した上で、Policy に基づいて操作可否を判断する。

---

# 13. 認可における基本原則

## 13.1 Authentication と Authorization を分離する

Authentication は Identity を確認し、Authorization は操作可否を判断する。

---

## 13.2 Global Role と Membership Role を分離する

プラットフォーム全体の役割と、Tenant 内の業務上の役割を混在させない。

---

## 13.3 Active Tenant を権限そのものとして扱わない

Active Tenant ID は現在の業務スコープを表すものであり、それ自体が権限を付与するものではない。

---

## 13.4 Tenant 境界を越えたアクセスを制限する

Tenant Scope における業務操作では、対象 Tenant に対する Membership を確認する。

---

## 13.5 Ownership を考慮する

同じ Role を持つ利用者であっても、Resource の所有・管理責任によって操作範囲が異なる場合がある。

---

## 13.6 最小権限の原則

利用者には、業務上必要な最小限の権限のみを付与する。

---

## 13.7 明示的な許可を基本とする

認可対象となる操作について、明示的に許可されていない操作は原則として拒否する。

---

# 14. 認可設計の責務分離

認可処理では、以下の責務を分離する。

```text
Authentication
      ↓
User Identity
      ↓
Authorization Context
      ↓
Policy
      ↓
Authorization Decision
```

各責務は以下のように整理する。

| 責務                     | 役割                                 |
| ---------------------- | ---------------------------------- |
| Authentication         | 利用者の Identity を確認する                |
| Scope                  | 現在の Tenant / Platform 範囲を特定する      |
| Membership             | Tenant への所属と Membership Role を確認する |
| Resource               | 対象 Resource を特定する                  |
| Ownership              | Resource の所有・管理責任を確認する             |
| Policy                 | 業務ルールに基づいて認可可否を判断する                |
| Authorization Decision | ALLOW / DENY を決定する                 |

具体的なクラス構成、Interface、Policy Engine、Repository 等は詳細設計で定義する。

---

# 15. 認可モデルの基本概念

本システムの認可モデルは、以下の関係を基本とする。

```text
                    ┌──────────────┐
                    │     User     │
                    └──────┬───────┘
                           │
                    Global Role
                           │
                           ▼
                    ┌──────────────┐
                    │    Tenant    │
                    └──────┬───────┘
                           │
                     Membership
                           │
                  Membership Role
                           │
                           ▼
                    ┌──────────────┐
                    │   Resource   │
                    └──────┬───────┘
                           │
                      Ownership
                           │
                           ▼
                         Action
                           │
                           ▼
                 Authorization Decision
```

このモデルにより、

* 誰が
* どの Tenant において
* どの役割を持ち
* どの Resource に対して
* どの操作を実行するか

を一貫したルールで判断できる構成とする。

---

# 16. 本章まとめ

Minshuku SaaS の Authentication / Authorization は、以下の基本方針で設計する。

```text
Authentication
      ↓
User Identity
      ↓
Authorization
      ↓
Global Role
      +
Membership Role
      +
Tenant Scope
      +
Resource Scope
      +
Ownership
      +
Action
      ↓
ALLOW / DENY
```

Authentication は利用者の Identity を確認し、Authorization はその Identity に基づいて業務操作の可否を判断する。

また、

```text
Global Role
      ≠
Membership Role
```

```text
Active Tenant
      ≠
Permission
```

```text
Role
      ≠
Ownership
```

を基本原則とする。

これにより、Platform Scope と Tenant Scope を明確に分離し、Tenant 内の Membership、Resource Scope、Ownership を考慮した安全かつ拡張可能な認可モデルを構築する。

# 05_テナント基本設計

## 1. 目的

本章では、Minshuku SaaS における Tenant を中心とした業務構造および基本的な管理方式を定義する。

本システムでは、Tenant を複数の利用者が共同で業務を行うための基本的な業務単位として扱う。

また、User、Tenant、Membership、Membership Role、Active Tenant、Business Resource の関係を明確にし、Tenant を基準とした業務スコープおよびデータ分離を実現する。

本章では Tenant に関する基本的な業務・システム構造を定義し、具体的なデータモデル、Class、Interface、Repository 等の詳細は 03_詳細設計で定義する。

---

# 2. Tenant の基本概念

Tenant は、Minshuku SaaS 上で一つの事業または業務組織を表す基本単位とする。

Tenant は、複数の User が所属し、Listing、Booking 等の業務を行うための境界となる。

基本的な関係は以下のとおりとする。

```text
Tenant
   │
   ├── Membership
   │       ├── User
   │       └── Membership Role
   │
   └── Business Resources
           ├── Listing
           ├── Booking
           └── Other Resources
```

Tenant は単なる User のグループではなく、業務上の責任範囲およびデータ管理範囲を定義する単位とする。

---

# 3. Tenant の役割

Tenant は、主に以下の役割を持つ。

### 3.1 業務組織の単位

Tenant は、宿泊事業等を運営する業務組織の単位として扱う。

---

### 3.2 利用者所属の単位

User がどの Tenant に所属しているかを Membership によって管理する。

---

### 3.3 業務リソースの管理単位

Listing、Booking 等の業務リソースは、原則として特定の Tenant と関連付ける。

---

### 3.4 権限スコープの単位

Tenant は、Tenant 内の業務操作における基本的な Authorization Scope とする。

---

### 3.5 データ分離の単位

Tenant に属する業務データについて、他の Tenant の業務データと不必要に混在・参照されないようにする。

---

# 4. User と Tenant の関係

User と Tenant は直接的な所属関係ではなく、Membership を介して関連付ける。

基本構造は以下のとおりとする。

```text
User
  │
  │
  ▼
Membership
  │
  │
  ▼
Tenant
```

1 人の User は、複数の Tenant に所属できるものとする。

また、1 つの Tenant は、複数の User を所属させることができる。

したがって、User と Tenant は多対多の関係を基本とし、その関係を Membership によって管理する。

```text
User
  │
  ├──── Membership ──── Tenant A
  │
  └──── Membership ──── Tenant B
```

---

# 5. Membership の基本設計

Membership は、User が特定の Tenant に所属していることを表す業務上の関係である。

Membership は、少なくとも以下の関係を表現する。

```text
User
+
Tenant
+
Membership Role
```

したがって、Membership は単なるアクセス許可情報ではなく、

> **「誰が、どの Tenant に、どの業務上の役割で所属しているか」**

を表す。

---

## 5.1 Membership の基本責務

Membership は、以下を管理する。

* User と Tenant の所属関係
* Tenant 内における Membership Role
* Membership の状態
* Membership の開始・終了等の所属情報

具体的な属性および状態管理については、Data 基本設計および詳細設計で定義する。

---

## 5.2 Membership の基本関係

```text
                 Tenant
                   │
        ┌──────────┼──────────┐
        │          │          │
        ▼          ▼          ▼
   Membership  Membership  Membership
        │          │          │
        ▼          ▼          ▼
      User       User       User
```

同一 User が複数の Tenant に所属する場合、それぞれの Tenant に対して Membership を持つ。

---

# 6. Membership Role

Membership Role は、特定 Tenant における User の業務上の役割を表す。

本システムでは、以下の Membership Role を基本とする。

```text
STAFF
MODERATOR
HOST
AGENT
OWNER
```

Membership Role は Global Role とは異なる概念として扱う。

```text
Global Role
    ↓
Platform における利用者の立場

Membership Role
    ↓
特定 Tenant における業務上の役割
```

---

## 6.1 STAFF

STAFF は、Tenant 内の日常的な業務を担当する利用者を表す。

具体的な操作範囲は、対象 Resource および Action に応じて定義する。

---

## 6.2 MODERATOR

MODERATOR は、Tenant 内のコンテンツや業務データの確認・管理等を担当する利用者を表す。

具体的な操作範囲は、対象 Resource および Action に応じて定義する。

---

## 6.3 HOST

HOST は、宿泊施設および Listing 等の運営業務を担当する利用者を表す。

主な業務対象：

* Listing 作成
* Listing 更新
* Listing 管理
* Listing 公開
* 担当する Resource の管理

---

## 6.4 AGENT

AGENT は、Tenant 内において宿泊事業の運営業務を支援する利用者を表す。

具体的な操作範囲は、対象 Resource、Action および Ownership に応じて定義する。

---

## 6.5 OWNER

OWNER は、Tenant における事業主体または管理責任者を表す。

Tenant 内の重要な業務管理について、必要な権限を持つものとする。

---

# 7. Global Role と Membership Role の関係

Global Role と Membership Role は、それぞれ異なる責務を持つ。

```text
Global Role
    │
    └── Platform 全体における利用者の立場

Membership Role
    │
    └── Tenant 内における利用者の業務上の役割
```

例えば、同一 User が複数の Tenant に所属する場合、それぞれの Tenant において異なる Membership Role を持つことができる。

```text
User
 │
 ├── Global Role: CUSTOMER
 │
 ├── Tenant A
 │      └── Membership Role: HOST
 │
 └── Tenant B
        └── Membership Role: STAFF
```

このように、Global Role は Tenant ごとに変化するものではなく、Membership Role は Tenant ごとに異なる場合がある。

---

# 8. Tenant Scope

Tenant Scope は、現在の業務操作がどの Tenant の範囲で実行されるかを示す。

Tenant Scope は Authorization における重要な境界である。

```text
User
  ↓
Active Tenant
  ↓
Tenant Scope
  ↓
Business Operation
```

Tenant Scope は権限そのものではない。

すなわち、

> **Active Tenant を指定したことだけでは、その Tenant に対する権限は付与されない。**

対象 Tenant に対する Membership および Membership Role 等を確認した上で、Authorization を判断する。

---

# 9. Active Tenant

Active Tenant は、利用者が現在操作対象としている Tenant を表す。

1 人の User が複数の Tenant に所属している場合、業務操作を行う際に対象となる Tenant を明確にする必要がある。

基本的な関係は以下のとおりとする。

```text
User
  │
  ├── Membership → Tenant A
  │
  ├── Membership → Tenant B
  │
  └── Active Tenant
           │
           └── Tenant A
```

Active Tenant は、現在の Request における業務スコープを示す。

---

## 9.1 Active Tenant の基本原則

Active Tenant について、以下を基本原則とする。

1. Active Tenant は業務操作の対象 Tenant を示す。
2. Active Tenant 自体は権限を付与しない。
3. Active Tenant と User の Membership を確認する。
4. 対象 Resource が Active Tenant に属していることを確認する。
5. Authorization Policy に基づいて最終的な操作可否を判断する。

---

# 10. Platform Scope と Tenant Scope

Authorization における Scope は、大きく Platform Scope と Tenant Scope に分ける。

```text
Scope
├── Platform Scope
└── Tenant Scope
```

---

## 10.1 Platform Scope

Platform Scope は、特定 Tenant に限定されないプラットフォーム全体の業務範囲を表す。

主に Platform Administration を対象とする。

```text
Platform
 ├── Tenant A
 ├── Tenant B
 ├── Tenant C
 └── ...
```

Platform Scope における権限は、Global Role および Action 等に基づいて判断する。

---

## 10.2 Tenant Scope

Tenant Scope は、特定の Tenant 内に限定された業務範囲を表す。

```text
Tenant A
 ├── Users
 ├── Listings
 ├── Bookings
 └── Other Resources
```

Tenant Scope における業務操作では、原則として対象 Tenant に対する Membership を必要とする。

---

# 11. Tenant と Business Resource の関係

Tenant に属する主要な Business Resource は、原則として Tenant との関係を明確にする。

例えば Listing の場合、

```text
Tenant
   │
   └── Listing
```

Booking の場合、

```text
Tenant
   │
   └── Booking
          │
          ├── User
          └── Listing
```

という業務関係を持つ。

これにより、Resource がどの Tenant の業務データであるかを明確にする。

---

# 12. Tenant と Ownership の関係

Tenant と Ownership は、別の概念として扱う。

```text
Tenant
   │
   └── Resource
          │
          └── Ownership
```

Tenant は業務組織上の境界を表す。

Ownership は、特定 Resource に対する所有または管理責任を表す。

したがって、

> **Tenant に所属していることと、Resource を所有・管理できることは同一ではない。**

例えば、同じ Tenant に所属する HOST が複数存在する場合、それぞれが管理できる Listing の範囲は Ownership 等によって異なる場合がある。

---

# 13. Tenant Isolation

Tenant Isolation は、Tenant 間の業務データおよび業務操作の境界を維持するための基本原則である。

基本的には、以下の関係を維持する。

```text
Tenant A
   │
   ├── Listing A
   ├── Booking A
   └── Other Data A


Tenant B
   │
   ├── Listing B
   ├── Booking B
   └── Other Data B
```

Tenant A の利用者が、正当な権限なしに Tenant B の業務データへアクセスできない構成とする。

---

## 13.1 Tenant Isolation の基本原則

1. Resource は所属 Tenant を識別できるものとする。
2. Tenant Scope を越えたアクセスを原則として許可しない。
3. Membership を確認した上で Tenant 内の操作を許可する。
4. Resource の Tenant 所属を確認する。
5. Ownership が必要な操作については Ownership を確認する。
6. Platform Scope を持つ管理操作については、別途明示的な認可ルールを定義する。

---

# 14. Tenant Lifecycle

Tenant は、業務上の状態を持つものとし、その状態に応じて利用可能な操作を制御する。

基本的な Lifecycle は以下を想定する。

```text
Creation
   ↓
Active
   ↓
Suspended
   ↓
Archived
```

---

## 14.1 Creation

Tenant が新規作成された状態。

必要な初期情報および初期管理者を設定する。

---

## 14.2 Active

通常の業務を実行できる状態。

Listing、Booking 等の Tenant 内業務を実行できる。

---

## 14.3 Suspended

一時的に業務利用を停止している状態。

Suspended 状態では、通常の業務操作を制限する。

---

## 14.4 Archived

業務上の利用を終了し、通常の業務操作を行わない状態。

既存データの保持、参照、監査等については、別途定義する。

---

# 15. Tenant 管理の基本原則

Tenant 管理では、以下の原則を採用する。

### 15.1 所属関係の明確化

User と Tenant の関係は Membership によって明確に管理する。

### 15.2 Role の分離

Global Role と Membership Role を混在させない。

### 15.3 Scope の明確化

Platform Scope と Tenant Scope を明確に分離する。

### 15.4 Resource の所属明確化

Business Resource がどの Tenant に属するかを明確にする。

### 15.5 Ownership の分離

Tenant 所属と Resource Ownership を同一概念として扱わない。

### 15.6 Tenant Isolation

Tenant 間の不正なデータ参照・操作を防止する。

### 15.7 最小権限

Tenant 内の利用者には、業務上必要な最小限の権限を付与する。

---

# 16. Tenant と Authorization の関係

Tenant は Authorization の重要な業務境界である。

認可判断では、以下の情報を組み合わせる。

```text
User
  +
Global Role
  +
Tenant Membership
  +
Membership Role
  +
Tenant Scope
  +
Resource Scope
  +
Ownership
  +
Action
```

概念的な処理は以下のとおりである。

```text
User
  ↓
Active Tenant
  ↓
Membership
  ↓
Membership Role
  ↓
Resource
  ↓
Ownership
  ↓
Action
  ↓
Authorization Decision
```

したがって、Tenant は単独で権限を付与するものではなく、Authorization を判断するための業務スコープとして機能する。

---

# 17. Tenant 設計の基本原則

本システムでは、以下の原則を Tenant 設計の基本とする。

### 17.1 Tenant を業務境界とする

Tenant を複数利用者による業務活動の基本単位とする。

### 17.2 Membership を所属関係とする

User と Tenant の関係は Membership によって表現する。

### 17.3 Membership Role を Tenant 内の役割とする

Tenant 内での業務上の役割は Membership Role によって表現する。

### 17.4 Active Tenant を業務スコープとする

Active Tenant は現在の業務操作対象を示し、権限そのものとはしない。

### 17.5 Resource Scope を明確にする

Business Resource の所属 Tenant を明確にし、Tenant 境界を維持する。

### 17.6 Ownership を独立して扱う

Resource の所有・管理責任は Tenant 所属とは別に扱う。

### 17.7 Platform Scope と Tenant Scope を分離する

Platform 全体の管理業務と Tenant 内の業務操作を明確に分離する。

---
