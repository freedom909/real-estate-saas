# 03-05_テナント詳細設計

## 1. 目的

本章では、02-05「テナント基本設計」で定義した Tenant、Membership、Membership Role、Tenant Scope、Active Tenant、Business Resource、Ownership 等の基本方針を、実装可能な詳細レベルまで具体化する。

本章では、Tenant に関する以下の詳細設計を定義する。

* Domain Entity
* Entity 間の関係
* Value Object
* Use Case
* Repository の責務
* Domain Service の責務
* Tenant Scope の扱い
* Active Tenant の扱い
* Membership の管理
* Membership Role の管理
* Tenant Lifecycle
* Validation
* Authorization との連携
* 業務処理フロー

本章では、具体的なデータベース製品、テーブル定義、GraphQL Schema、Framework 固有の実装方式については定義しない。

---

# 2. 基本設計から詳細設計への導出

本詳細設計は、02-05「テナント基本設計」で定義した以下の原則を基礎とする。

```text
User
  ↓
Membership
  ↓
Tenant
  ↓
Membership Role
  ↓
Tenant Scope
  ↓
Business Resource
  ↓
Ownership
```

基本設計で定義された概念を、詳細設計では以下のように具体化する。

| 基本設計                              | 詳細設計                         |
| --------------------------------- | ---------------------------- |
| Tenant は業務単位                      | Tenant Entity                |
| User と Tenant は Membership で関連付ける | Membership Entity            |
| Membership Role は Tenant 内の役割     | Membership Role              |
| Active Tenant は業務スコープ             | Tenant Scope                 |
| Resource は Tenant に所属する           | Resource Tenant Association  |
| Ownership は別概念                    | Ownership 情報                 |
| Tenant Lifecycle を管理する            | Tenant State                 |
| Tenant Isolation を維持する            | Scope Validation             |
| Tenant と Authorization を連携する      | Authorization Context への情報提供 |

したがって、詳細設計では基本設計で定義されていない新しい業務ルールを追加しないものとする。

---

# 3. Domain 構成

Tenant Domain は、以下の主要概念から構成する。

```text
Tenant Domain
│
├── Tenant
│
├── Membership
│
├── Membership Role
│
├── Tenant Status
│
└── Tenant Scope
```

User は User Domain の責務として管理し、Tenant Domain は User の詳細プロフィール等を管理しない。

```text
User Domain
     │
     │ User ID
     ▼
Tenant Domain
     │
     ├── Membership
     ├── Tenant
     └── Membership Role
```

---

# 4. Tenant Entity

## 4.1 責務

Tenant Entity は、一つの業務組織または事業単位を表現する。

Tenant Entity は、Tenant 自身の業務状態および Tenant に関する基本的な不変条件を管理する。

---

## 4.2 主な責務

Tenant Entity は、以下を担当する。

* Tenant の識別
* Tenant の基本状態管理
* Tenant Lifecycle の状態管理
* Tenant の有効性判定
* Tenant に関する基本的な状態遷移

User の認証情報や Membership の詳細な権限判断は Tenant Entity の責務としない。

---

## 4.3 Tenant の概念属性

Tenant Entity は、概念上、以下の情報を持つ。

```text
Tenant
├── Tenant ID
├── Tenant Name
├── Tenant Status
├── Created At
└── Updated At
```

具体的なデータ型および永続化形式は Data 詳細設計で定義する。

---

# 5. Tenant Status

Tenant の Lifecycle を管理するため、Tenant Status を定義する。

基本状態は以下とする。

```text
CREATION
ACTIVE
SUSPENDED
ARCHIVED
```

---

## 5.1 状態遷移

```text
CREATION
    │
    ▼
  ACTIVE
   │   │
   │   ▼
   │ SUSPENDED
   │    │
   │    ▼
   │  ACTIVE
   │
   ▼
ARCHIVED
```

ARCHIVED から ACTIVE への通常の状態復帰は、原則として行わない。

---

## 5.2 状態ごとの基本動作

| Status    | 基本動作       |
| --------- | ---------- |
| CREATION  | 初期設定を行う    |
| ACTIVE    | 通常業務を実行できる |
| SUSPENDED | 通常業務を制限する  |
| ARCHIVED  | 通常業務を終了する  |

状態ごとの詳細な操作制限は、各業務 Use Case の Authorization Rule と組み合わせて定義する。

---

# 6. Membership Entity

## 6.1 責務

Membership Entity は、User と Tenant の所属関係を表現する。

```text
User
  │
  ▼
Membership
  │
  ▼
Tenant
```

Membership は、以下の関係を一つの業務単位として扱う。

```text
User
+
Tenant
+
Membership Role
+
Membership Status
```

---

## 6.2 Membership の主な責務

Membership は、以下を担当する。

* User の Tenant 所属
* Tenant における Membership Role
* Membership の状態
* Membership の開始・終了
* Membership の有効性

User 自身のプロフィール管理は担当しない。

Tenant 自体の Lifecycle 管理も担当しない。

---

# 7. Membership Role

Membership Role は、特定 Tenant 内における User の業務上の役割を表す。

基本 Role は以下とする。

```text
STAFF
MODERATOR
HOST
AGENT
OWNER
```

Membership Role は Tenant 単位で保持する。

```text
User
 │
 ├── Tenant A
 │      └── HOST
 │
 └── Tenant B
        └── STAFF
```

同一 User が複数 Tenant に所属する場合、それぞれ異なる Membership Role を持つことができる。

---

# 8. Membership Status

Membership は、所属状態を管理するための Status を持つ。

詳細な状態名称は業務要件に応じて定義するが、基本的には以下の状態を想定する。

```text
PENDING
ACTIVE
SUSPENDED
REMOVED
```

---

## 8.1 基本状態

### PENDING

Membership が作成されたが、まだ有効化されていない状態。

### ACTIVE

Tenant 内で有効な Membership として利用できる状態。

### SUSPENDED

一時的に Tenant 内の業務操作を利用できない状態。

### REMOVED

Tenant との所属関係が終了した状態。

---

# 9. Membership の一意性

同一 User が同一 Tenant に対して複数の Active Membership を持つことは原則として認めない。

基本的な業務上の一意性は以下とする。

```text
User
+
Tenant
=
一つの Membership
```

ただし、過去の Membership 履歴を保持する場合、履歴上複数の Membership Record が存在することは許容する。

この場合でも、同一時点で有効な Membership は一つに限定する。

---

# 10. Tenant Scope

Tenant Scope は、現在の業務処理が対象とする Tenant の範囲を表現する。

詳細設計では、Tenant Scope を以下の情報として扱う。

```text
Tenant Scope
├── Scope Type
└── Tenant ID
```

Scope Type は以下を基本とする。

```text
PLATFORM
TENANT
```

---

## 10.1 Platform Scope

Platform Scope は、特定 Tenant に限定されない業務処理を表す。

```text
Scope Type = PLATFORM
```

Platform Scope では、Tenant ID を必須情報とはしない。

---

## 10.2 Tenant Scope

Tenant Scope は、特定 Tenant を対象とした業務処理を表す。

```text
Scope Type = TENANT
Tenant ID = Target Tenant
```

Tenant Scope における業務操作では、対象 Tenant に対する Membership を確認する。

---

# 11. Active Tenant

Active Tenant は、Request または Session において現在操作対象となっている Tenant を表す。

Active Tenant は、以下の情報から構成される。

```text
Active Tenant
    ↓
Tenant ID
```

Active Tenant は Authorization の入力情報となるが、それ自体は権限ではない。

```text
Active Tenant
      ≠
Permission
```

---

## 11.1 Active Tenant の設定

User が複数の Tenant に所属している場合、業務操作の対象 Tenant を明示的に選択できる。

```text
User
 │
 ├── Tenant A
 ├── Tenant B
 └── Tenant C
          │
          ▼
    Active Tenant
          │
          ▼
       Tenant C
```

---

## 11.2 Active Tenant の検証

Active Tenant が指定された場合、以下を検証する。

```text
1. Tenant が存在する
2. Tenant が利用可能な状態である
3. User が Tenant に所属している
4. Membership が有効である
5. 対象 Resource が Tenant に属している
```

必要な場合、さらに Membership Role および Ownership を Authorization Policy によって検証する。

---

# 12. Tenant と Resource の関係

Tenant に属する Business Resource は、原則として Tenant との所属関係を持つ。

```text
Tenant
   │
   ├── Listing
   ├── Booking
   ├── Review
   └── Other Business Resources
```

Resource は、どの Tenant に属しているかを識別できる必要がある。

---

## 12.1 Resource 所属の原則

Resource に対する Tenant Scope の検証では、

```text
Request Tenant
      =
Resource Tenant
```

であることを基本条件とする。

一致しない場合、Tenant Scope を越えたアクセスとして扱う。

---

# 13. Ownership

Ownership は、Resource に対する所有または管理責任を表現する。

Ownership は Tenant Membership とは独立した概念とする。

```text
Tenant Membership
        ≠
Resource Ownership
```

例えば、

```text
Tenant A
   │
   ├── User A ── HOST
   ├── User B ── HOST
   │
   └── Listing
          │
          └── Owner = User A
```

この場合、User B が Tenant A の Membership を持っていることだけでは、User A が所有する Listing を自由に管理できることを意味しない。

---

# 14. Tenant Authorization Context

Authorization を実行する際、Tenant に関する情報を Authorization Context に渡す。

概念的には以下の構造とする。

```text
Authorization Context
│
├── Subject
│     └── User ID
│
├── Global Role
│
├── Scope
│     ├── Scope Type
│     └── Tenant ID
│
├── Membership
│     ├── Tenant ID
│     └── Membership Role
│
└── Resource
      ├── Resource ID
      ├── Tenant ID
      └── Owner ID
```

この Context を利用して Authorization Policy が操作可否を判断する。

---

# 15. Tenant Repository

Tenant Repository は、Tenant の永続化および取得に関する責務を担当する。

Repository は、Domain の業務ルールそのものを判断しない。

主な責務：

* Tenant の取得
* Tenant の保存
* Tenant の更新
* Tenant の状態取得
* Tenant の存在確認

Repository は Infrastructure 層に配置する。

---

# 16. Membership Repository

Membership Repository は、User と Tenant の所属関係を取得・管理する。

主な責務：

* User による Membership 検索
* Tenant による Membership 検索
* User と Tenant による Membership 検索
* Active Membership の確認
* Membership の保存
* Membership の更新

Repository は Membership のデータ取得を担当するが、

> **「この操作を許可するか」**

という Authorization Decision 自体は担当しない。

---

# 17. Tenant Use Case

Tenant に関する主要な Use Case は以下とする。

```text
Tenant
├── Create Tenant
├── Read Tenant
├── Update Tenant
├── Suspend Tenant
├── Activate Tenant
└── Archive Tenant
```

Membership に関する Use Case は以下とする。

```text
Membership
├── Add Member
├── Read Membership
├── Update Membership Role
├── Suspend Membership
├── Activate Membership
└── Remove Membership
```

---

# 18. Tenant 作成処理

Tenant 作成処理は、以下の流れを基本とする。

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Validate Tenant Input
   ↓
Create Tenant
   ↓
Create Initial Membership
   ↓
Set Initial Membership Role
   ↓
Save
   ↓
Return Tenant
```

Tenant 作成時に初期管理者または初期 Membership を設定する場合、その関係を明確にする。

具体的な初期 Role および作成権限は Authorization 詳細設計で定義する。

---

# 19. Membership 作成処理

Membership 作成処理は、以下を基本とする。

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Validate Tenant
   ↓
Validate User
   ↓
Check Existing Membership
   ↓
Create Membership
   ↓
Assign Membership Role
   ↓
Save
```

同一 User と Tenant の間に有効な Membership が既に存在する場合、重複した Membership を作成しない。

---

# 20. Membership Role 変更処理

Membership Role の変更は、Tenant 内の業務権限に影響するため、通常のプロフィール更新とは分離した Use Case とする。

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Find Membership
   ↓
Validate Target Role
   ↓
Update Membership Role
   ↓
Save
   ↓
Audit
```

Role 変更の実行可否は、対象 Tenant、実行者の Membership Role、Global Role、および Action に基づいて Authorization で判断する。

---

# 21. Membership 削除処理

Membership の削除は、User と Tenant の所属関係を終了させる操作である。

基本的には物理削除ではなく、所属状態を終了状態へ変更する方式を基本とする。

```text
ACTIVE
   ↓
REMOVED
```

ただし、データ保持要件により物理削除が必要となる場合は、別途定義する。

---

# 22. Tenant Lifecycle 処理

Tenant Lifecycle の状態変更は、明示的な Use Case として扱う。

```text
Create
  ↓
CREATION
  ↓
Activate
  ↓
ACTIVE
  │
  ├── Suspend
  │      ↓
  │   SUSPENDED
  │      │
  │      └── Activate
  │              ↓
  │            ACTIVE
  │
  └── Archive
         ↓
      ARCHIVED
```

各状態変更について、Authorization および業務上の事前条件を確認する。

---

# 23. Validation

Tenant Domain では、以下の基本的な Validation を行う。

## 23.1 Tenant Validation

* Tenant ID が一意であること
* 必須情報が設定されていること
* Tenant Status が有効な状態であること

## 23.2 Membership Validation

* User が存在すること
* Tenant が存在すること
* User と Tenant の関係が重複していないこと
* Membership Role が有効な値であること
* Membership Status が有効な状態であること

## 23.3 Scope Validation

* Active Tenant が存在すること
* Active Tenant が対象 Tenant と一致すること
* User が対象 Tenant に所属していること
* Membership が有効であること

## 23.4 Resource Validation

* Resource が存在すること
* Resource が対象 Tenant に属していること
* 必要に応じて Ownership が一致すること

---

# 24. Tenant Isolation の処理原則

Tenant Scope の業務操作では、以下の順序で境界を確認する。

```text
User Identity
     ↓
Target Tenant
     ↓
Membership
     ↓
Membership Role
     ↓
Resource Tenant
     ↓
Ownership
     ↓
Action
     ↓
Authorization Decision
```

この順序により、Tenant 外の Resource に対して業務操作が実行されることを防止する。

---

# 25. Platform Scope の処理

Platform Scope における操作では、特定 Tenant の Membership を必須条件としない場合がある。

```text
Platform Scope
      ↓
Global Role
      ↓
Action
      ↓
Authorization Decision
```

ただし、Platform Scope を持つこと自体がすべての操作を許可することを意味しない。

操作単位で Authorization Policy を適用する。

---

# 26. Tenant Scope の処理

Tenant Scope における操作では、原則として以下を確認する。

```text
Tenant Scope
      ↓
Target Tenant
      ↓
Membership
      ↓
Membership Role
      ↓
Resource
      ↓
Ownership
      ↓
Action
```

これにより、同一 User が複数 Tenant に所属する場合でも、現在操作している Tenant の範囲を明確に維持する。

---

# 27. Domain Service の責務

複数の Entity または Domain Object にまたがる Tenant 固有の業務ルールが必要な場合、Domain Service を利用する。

Domain Service は、単一 Entity に自然に帰属しない業務ルールを担当する。

例えば、

* Tenant と Membership の関係検証
* Tenant Lifecycle に関する複合ルール
* Membership 状態と Tenant 状態の整合性確認

等を対象とする。

ただし、Authorization の最終判断は Authorization Policy の責務とする。

---

# 28. Application Layer の責務

Application Layer は、Tenant に関する業務処理のユースケースを実行する。

主な責務：

```text
Input
 ↓
Use Case
 ↓
Repository
 ↓
Domain
 ↓
Authorization
 ↓
Output
```

Application Layer は、以下を調整する。

* Authentication Context の受け取り
* Tenant Scope の確定
* Repository の呼び出し
* Domain Object の操作
* Authorization との連携
* Transaction 境界の管理
* 結果の返却

---

# 29. Presentation / API Layer の責務

API Layer は、外部からの Request を受け取り、Application Layer に処理を委譲する。

API Layer は、Tenant Domain の業務ルールを直接実装しない。

基本構造は以下とする。

```text
Client
  ↓
API
  ↓
Authentication
  ↓
Application Use Case
  ↓
Tenant Domain
  ↓
Repository
```

GraphQL Resolver 等は、Tenant Domain の内部構造を直接操作しない。

---

# 30. Audit との連携

Tenant に関する重要な管理操作については、Audit Domain と連携する。

対象となる操作の例：

* Tenant 作成
* Tenant 状態変更
* Membership 作成
* Membership Role 変更
* Membership 停止
* Membership 削除
* その他の管理操作

基本的な処理は以下とする。

```text
Business Operation
      ↓
Authorization
      ↓
Execute Operation
      ↓
Audit Event
```

Audit は Tenant Domain の業務ルールを判断する責務を持たない。

---

# 31. Tenant 詳細設計における責務分離

各レイヤの責務を以下のように分離する。

| レイヤ                | 主な責務                       |
| ------------------ | -------------------------- |
| API / Presentation | Request の受付                |
| Authentication     | User Identity の確認          |
| Application        | Use Case の調整               |
| Tenant Domain      | Tenant / Membership の業務ルール |
| Authorization      | 操作可否の判断                    |
| Repository         | データの取得・保存                  |
| Infrastructure     | 永続化・外部技術への接続               |
| Audit              | 重要操作の記録                    |

特に、

```text
Membership Repository
      ≠
Authorization Policy
```

を明確にする。

Repository は Membership を取得する。

Authorization Policy は、その情報を利用して操作可否を判断する。

---

# 32. 詳細処理モデル

Tenant Scope における代表的な業務処理は、以下の構造とする。

```text
Request
   ↓
Authentication
   ↓
User Identity
   ↓
Determine Active Tenant
   ↓
Load Membership
   ↓
Load Resource
   ↓
Build Authorization Context
   ↓
Authorization Policy
   ↓
ALLOW / DENY
   ↓
Execute Use Case
   ↓
Persist Changes
   ↓
Audit
   ↓
Response
```

Authorization に失敗した場合、業務処理は実行しない。

---

# 33. エラー処理の基本方針

Tenant Domain では、以下の種類のエラーを区別する。

```text
Authentication Error
Authorization Error
Tenant Not Found
Membership Not Found
Invalid Membership
Invalid Tenant State
Resource Not Found
Tenant Scope Violation
Validation Error
```

特に、

> **「Resource が存在しない」**

ことと、

> **「Resource は存在するが、Tenant Scope 外である」**

ことは、内部的な業務エラーとして区別する。

外部 API に返却するエラー情報については API 詳細設計で定義する。

---

# 34. 詳細設計上の禁止事項

Tenant Domain では、以下の設計を避ける。

### 34.1 User Role だけで Tenant 権限を判断しない

```text
User Role
    ↓
ALLOW
```

という単純な判断を行わない。

---

### 34.2 Active Tenant を権限として扱わない

```text
Active Tenant
    ↓
Permission Granted
```

という設計を行わない。

---

### 34.3 Membership と Ownership を混同しない

```text
Membership
    =
Ownership
```

とは扱わない。

---

### 34.4 Repository に Authorization Logic を実装しない

Repository はデータ取得・保存を担当し、Authorization Decision は担当しない。

---

### 34.5 API Layer に業務ルールを集中させない

Tenant の業務ルールを Resolver や Controller に直接実装しない。

---

# 35. 基本設計からの推論結果

02-05 の基本設計から、詳細設計では以下の構造が導かれる。


# 36. 本章まとめ

Tenant の詳細設計は、02-05「テナント基本設計」で定義された業務概念を、実装可能な責務と処理単位へ具体化する。

基本的な構造は以下とする。

```text
User
  ↓
Membership
  ↓
Tenant
  ↓
Membership Role
  ↓
Tenant Scope
  ↓
Business Resource
  ↓
Ownership
```

Application 処理では、以下の流れを基本とする。

```text
Request
  ↓
Authentication
  ↓
Active Tenant
  ↓
Membership
  ↓
Resource
  ↓
Authorization Context
  ↓
Authorization Policy
  ↓
Business Use Case
  ↓
Repository
  ↓
Audit
```

また、以下の責務分離を維持する。

```text
Authentication
      ≠
Authorization

Membership
      ≠
Ownership

Tenant Scope
      ≠
Permission

Repository
      ≠
Authorization Policy
```

本詳細設計により、02-05 で定義した Tenant の基本概念を、Application、Domain、Authorization、Repository、Audit 等の具体的な責務へ段階的に落とし込む。

次段階では、本設計に基づいて Data 詳細設計、API 詳細設計、Authorization 詳細設計等を定義する。
