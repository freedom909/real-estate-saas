### Create-Listing 403 Fix (2026-10-27)
- **Root cause**: `uploadClient` (`frontend/app/lib/apolloClient.ts`) hits listing subgraph :4101 DIRECTLY (Apollo Gateway can't forward multipart uploads), but commit `e166040` added `verifyInternalServiceRequest` to every subgraph `/graphql` route — requires `x-service-token` header or returns raw HTTP 403. Browser never sends that token → `ServerError: Received status code 403` on every `uploadClient` mutation (createListing with files, uploadImages).
- **Fix**: new proxy route `frontend/app/api/graphql-upload/route.ts` — same-origin POST handler that relays GraphQL (multipart via `formData()` re-send, or JSON passthrough) to the listing subgraph and attaches `x-service-token` + forwarded `Authorization` server-side. `uploadClient` UploadHttpLink uri → `/api/graphql-upload`. Token copied into `frontend/.env.local` as `INTERNAL_SERVICE_TOKEN` (server-side only, NOT `NEXT_PUBLIC_`).
- **Security invariant preserved**: subgraphs stay internal-only; internal token never enters the browser bundle.
- **Note**: plain `client` (default) mutations go through gateway :4000 and were never affected (gateway's `willSendRequest` sets `x-service-token`, `gateway/index.ts:179-185`). Build ✅ 54 routes.

### "Active tenant is required" Fix (2026-10-27)
- **Root cause** (after 400 fixed): `context.user.tenantId` comes **exclusively** from the `x-tenant-id` request header (`getUserFromContext.ts:14,64` — NOT from the JWT). Only the gateway sets it (auth.plugin looks up Mongo `Session.activeTenantId`). Three gaps:
  1. Sessions are created with `activeTenantId: null` (`session.service.ts:90`) and login never auto-selects a tenant (plan doc step "Login → auto-select first tenant → store in Session" was NOT implemented).
  2. `tenant-sync.tsx` only mirrored selection into zustand (`setActiveTenant`) — never persisted to Session via `switchTenant` REST.
  3. `/api/graphql-upload` proxy forwarded `authorization` but not `x-tenant-id`.
- **Fixes**:
  - `frontend/app/auth/tenant-sync.tsx` — on sync: if session has valid active tenant → mirror locally; else persist `localActiveId` (remembered) or `tenants[0]` to the Session via `switchTenant()` REST (validates membership server-side) — auto-select at login.
  - `frontend/app/api/graphql-upload/route.ts` — resolves caller's tenant via `GET {GATEWAY_URL}/api/tenants/active` (same Session record the gateway uses; `tenantRouter.ts:254` returns `{ activeTenantId }`) and forwards it as `x-tenant-id`.
  - `frontend/app/listing/new/page.tsx` (standalone legacy form, uses default client → gateway) — input now sends `tenantId: activeTenantId` and `pictures: [{objectKey, mimeType: "image/png", size: 0}]` (was missing required `CreateImageInput` fields).
- **Key architecture**: `Session.activeTenantId` (Mongo) is the single source of truth for tenant scoping; `POST /api/tenants/switch` is the ONLY writer (validates membership). Gateway auth.plugin + the upload proxy both read it per-request.
- **Caveat**: `/listing/new` sends `locationId: form.locationId || "default-location"` (fake fallback id) — may fail location validation in the usecase; use a real location id.

### "memberships.findOne() buffering timed out" Fix (2026-10-27)
- **Root cause (2 layers)**:
  1. The listing subgraph (:4101) **never connected mongoose** — startup only ran `sequelize` (MySQL). `MembershipModel`/`TenantModel` (registered via `registerUserDependencies`) live on the default mongoose connection, so `resolveAuthorizationIdentity` → `memberships.findOne()` buffered until Mongoose's 10s timeout. (Booking/review subgraphs call `initMongoContainer()` at startup; listing omitted it.)
  2. Wiring `initMongoContainer()` in alone wasn't enough: this machine's local DNS can't resolve the Atlas SRV record (`querySrv ECONNREFUSED _mongodb._tcp.cluster0.oyfic.mongodb.net`). `connectMongoDB.ts` has `dns.setServers(["8.8.8.8"])` for exactly this; `initMongoContainer` lacked it → subgraph aborted boot at connect.
- **Fixes**:
  - `src/subgraphs/listing/index.ts` — `await initMongoContainer()` in `startApolloServer` before serving (pattern: booking/review).
  - `src/infrastructure/container/initMongoContainer.ts` — added `dns.setServers(["8.8.8.8"])` (same workaround as `connectMongoDB.ts`); fixes listing + booking + review on machines where local DNS can't resolve Atlas SRV.
- **Verified live**: minted-JWT probe to :4101 → before: 10s buffering timeout; after: **282ms**, business error `"Membership role cannot create listings"` (authz layer working — probe user had no HOST membership). Mongo db = `sendai`, `memberships` collection confirmed present. Listing resolver tests 20/20 ✅.

# AI Platform Context — Wisdom Refactor

## Architecture
- **Entry**: `src/wisdom/index.ts` — Express + Apollo Server (subgraph) on port 4200
- **Dev script**: `npm run dev:ai` or `npm run dev:wisdom` (both point to `src/wisdom/index.ts`)
- **DI**: tsyringe container, registered via `src/wisdom/container/registrations/wisdom.register.ts`
- **Auth**: `getUserFromToken(req)` extracts JWT from `Authorization: Bearer <token>` header
- **Flow**: Resolver → ChatUseCase → WisdomOrchestrator → SemanticExtractor → ReferenceResolver → AgentRouter → Agent → **KnowledgeExtractor** → KnowledgeStore → WisdomResponse

## Key Tokens
- `TOKENS_USER.repos.userRepository` → `Symbol.for("UserRepository")`
- `TOKENS_USER.usecase.becomeHostUseCase` → `Symbol.for("user.usecase.becomeHostUseCase")`
- `TOKENS_ADMIN.usecase.getAllAdminsUseCase` → `Symbol.for("GetAllAdminsUseCase")`
- `TOKENS_CALENDAR.usecase.reserveSlotUseCase` → `Symbol.for("ReserveSlotUseCase")`

## Key API Changes
- `MemorySessionStore`: uses `get(sessionId)`, `getOrCreate(sessionId)`, `set(sessionId, state)` — NO `load(ctx)`
- `UserRepository`: named export (not default), uses `findByEmail` (not `userByEmail`), 1-arg constructor (model only)
- `UserService`: uses `findByEmail` (not `userByEmail`), has `deactivate` method
- `ListingReferenceResolver`: renamed from `ReferenceResolver`, 1-arg constructor (searchListingUseCase)
- `ReferenceResolver` (conversation): 2-arg constructor (listingReferenceResolver + conversationReferenceResolver)
- `bookingReducer`: only handles `SELECT_LISTING` event — `SET_DATES` falls through to default
- `ROLE_HIERARCHY`: GUEST=0, CUSTOMER=1, STAFF=2, MODERATOR=3, HOST=4, AGENT=5, OWNER=6, ADMIN=7, SUPER_ADMIN=8
