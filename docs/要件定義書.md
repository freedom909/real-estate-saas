## Block 1：ユーザー・認証・認可・セッション

# 1. ユーザー・認証・認可・セッション要件

## 1.1 対象範囲

本機能は、宿泊施設予約・管理SaaSにおけるユーザーの本人認証、ユーザー情報管理、ロール管理、OAuth認証、セッション管理および認可制御を対象とする。

対象範囲は以下とする。

- ユーザー管理
- ユーザープロフィール管理
- OAuth認証
- OAuth Identity管理
- グローバルロール管理
- アカウントステータス管理
- セッション管理
- Access Token / Refresh Token管理
- ログアウト
- リスクベース認証
- OTPによる追加認証
- Trusted Device管理
- APIアクセス時の認可制御

***

# 2. ユーザー要件

## USR-001 ユーザー一意性

システムは、各ユーザーを一意に識別できるユーザーIDを付与する。

ユーザーIDを利用して、ユーザー情報、OAuth Identity、Session、Booking等の関連情報を識別できるものとする。

***

## USR-002 ユーザー基本情報

システムは、ユーザーについて以下の基本情報を管理する。

- ユーザーID
- メールアドレス
- 氏名
- ロール
- アカウントステータス
- 有効／無効状態
- 作成日時
- 更新日時

***

## USR-003 プロフィール管理

ユーザーは、自身のプロフィール情報を管理できるものとする。

現行システムにおける基本プロフィール情報は以下とする。

- 氏名
- メールアドレス
- アバター

電話番号、住所等については将来拡張項目とし、本要件の必須対象外とする。

***

## USR-004 アカウントステータス

システムは、ユーザーのアカウント状態を管理する。

アカウント状態は、ユーザーのロールとは独立して管理するものとする。

例：

- ACTIVE
- SUSPENDED
- INACTIVE
- BANNED
- DELETED

※ 実装上の状態値については、現行コードとの最終照合を行い確定する。

***

# 3. ロール管理要件

## ROLE-001 グローバルロール

システムはユーザー単位でグローバルロールを管理する。

現行システムで確認されている主なロールは以下とする。

- GUEST
- CUSTOMER
- STAFF
- MODERATOR
- HOST
- AGENT
- OWNER
- ADMIN
- SUPER\_ADMIN

***

## ROLE-002 新規ユーザーのデフォルトロール

OAuth等によって新規ユーザーが作成された場合、特別な権限付与処理がない限り、デフォルトロールを `CUSTOMER` とする。

***

## ROLE-003 ロールとアカウント状態の分離

ロールは「ユーザーがどのような権限を持つか」を表し、アカウント状態は「現在システムを利用可能か」を表すものとする。

したがって、以下のような状態を許容する。

```text
HOST + ACTIVE
HOST + SUSPENDED
ADMIN + ACTIVE
ADMIN + SUSPENDED
```

***

## ROLE-004 CustomerからHostへの変更

Customerは、所定の条件を満たした場合、Hostへ変更できるものとする。

***

## ROLE-005 管理者権限の付与

Admin等の高権限ロールへの変更は、変更を実行するユーザー自身の権限を検証した上で実行するものとする。

クライアントから任意の高権限ロールを指定して昇格できてはならない。

***

# 4. OAuth認証要件

## AUTH-001 OAuthログイン

システムはOAuth Providerを利用したログインを提供する。

現行実装で主要対象となっているProviderは以下とする。

- Google
- GitHub
- Facebook

Apple、LINE等についてはスキーマ上の定義と実装状況を分離して管理し、正式提供範囲は別途確定する。

***

## AUTH-002 OAuth Credential

OAuthログイン時には、Providerに応じたCredentialを使用して本人認証を行う。

Credentialとして以下を扱えるものとする。

- Authorization Code
- Access Token
- ID Token

Providerごとに必要なCredentialの種類を判定するものとする。

***

## AUTH-003 OAuth Identity

システムは、外部OAuthアカウントと内部Userとの関連をOAuth Identityとして管理する。

OAuth Identityは以下の情報を基本とする。

- Identity ID
- User ID
- Provider
- Provider User ID
- Email
- 作成日時

***

## AUTH-004 OAuth Identityの一意性

OAuth Identityは、

```text
Provider + Provider User ID
```

の組み合わせによって一意に識別する。

***

## AUTH-005 既存Identityによるログイン

OAuthログイン時に既存のOAuth Identityが存在する場合、新規Userを作成せず、既存Userを使用してログインする。

***

## AUTH-006 新規User作成

OAuth Identityが存在せず、既存Userとの安全な関連付けもできない場合、新規Userを作成する。

新規Userのデフォルトロールは `CUSTOMER` とする。

***

## AUTH-007 Emailによる既存Userとの関連付け

OAuth Providerから取得したEmailが既存Userと一致する場合、一定の安全条件を満たす場合に限り、既存UserへOAuth Identityを関連付けることができる。

Provider側でEmailがVerifiedであることを確認する等、安全条件を設けるものとする。

***

# 5. 認証リスク管理要件

## AUTH-101 リスク評価

OAuth認証成功後、システムは必要に応じてログインリスクを評価する。

リスク判定結果は概念上以下の3種類とする。

```text
ALLOW
CHALLENGE
BLOCK
```

***

## AUTH-102 ALLOW

リスク判定結果が `ALLOW` の場合、通常のログイン処理を継続し、Sessionを発行する。

***

## AUTH-103 CHALLENGE

リスク判定結果が `CHALLENGE` の場合、追加認証を要求する。

追加認証にはOTP Challengeを使用する。

***

## AUTH-104 BLOCK

リスク判定結果が `BLOCK` の場合、ログインを拒否する。

BLOCK判定されたユーザーについて、通常の認証Sessionを発行してはならない。

***

# 6. OTP認証要件

## OTP-001 OTP Challenge

システムは、追加認証が必要な場合にOTP Challengeを生成する。

Challengeには少なくとも以下を関連付ける。

- User
- Device
- Challenge Type
- Status
- Expiration Time

***

## OTP-002 OTP有効期限

OTP Challengeには有効期限を設定する。

現行実装では5分を基本値としている。

***

## OTP-003 OTP成功

OTP認証に成功した場合、Challengeを完了状態とし、所定のSession発行処理へ進む。

***

## OTP-004 OTP失敗

OTP認証に失敗した場合、認証処理を完了させてはならない。

***

# 7. セッション管理要件

## SES-001 Session生成

認証に成功したユーザーについてSessionを生成する。

SessionはUserと関連付ける。

***

## SES-002 Session情報

Sessionには、必要に応じて以下の情報を保持する。

- Session ID
- User ID
- Device ID
- IP Address
- User Agent
- Created At
- Last Seen At
- Expiration
- Revoked At
- Session Status
- Active Tenant ID
- Refresh Token情報

***

## SES-003 Access Token

認証済みユーザーに対してAccess Tokenを発行する。

Access Tokenには少なくとも以下の認証情報を含める。

- User ID
- Session ID
- Token Type
- Role
- Email等の必要なUser情報

***

## SES-004 Refresh Token

システムはAccess Tokenの更新に使用するRefresh Tokenを提供する。

Refresh TokenはAccess Tokenとは異なるToken Typeとして管理する。

***

## SES-005 Token Type検証

APIアクセス時にはToken Typeを検証する。

Access APIにRefresh Tokenを使用してはならない。

***

## SES-006 Session検証

認証済みAPIへのアクセス時には、JWTの署名検証だけでなく、関連するSessionの存在および有効性を確認する。

***

## SES-007 Revoked Session

Revoked状態となったSessionは、以後の認証済みAPIアクセスに利用できないものとする。

***

## SES-008 Token Blacklist

必要に応じてToken Blacklistを利用し、無効化されたTokenによるアクセスを拒否できるものとする。

***

# 8. ログアウト要件

## SES-101 Logout

認証済みユーザーは自身のSessionをLogoutできるものとする。

***

## SES-102 Logout後のSession

LogoutされたSessionはRevoked状態となり、当該Sessionに関連するAccess TokenによるAPIアクセスを拒否する。

***

# 9. Trusted Device要件

## SEC-001 Device Identification

システムは、ログイン端末を識別するためDevice ID / Device Fingerprint等の情報を利用できるものとする。

***

## SEC-002 Trusted Device

追加認証を正常に完了した端末について、Trusted Deviceとして登録できるものとする。

Trusted Device情報はUserおよびDeviceと関連付けて管理する。

***

# 10. 認可要件

## SEC-101 認証と認可の分離

認証（Authentication）と認可（Authorization）は分離して管理する。

Authentication：

> 「このユーザーは誰か」

Authorization：

> 「このユーザーは何を実行できるか」

***

## SEC-102 Role-based Authorization

保護対象APIでは、User Roleに基づいてアクセス権限を判定する。

***

## SEC-103 Resource Ownership

Roleだけではなく、対象Resourceの所有者であるかどうかを必要に応じて確認する。

***

## SEC-104 権限昇格防止

通常ユーザーがリクエストパラメータを変更するだけでADMIN、OWNER、SUPER\_ADMIN等の高権限Roleを取得できてはならない。

***

# 11. 非機能・セキュリティ要件

## NFR-SEC-001

JWTの署名検証を必須とする。

## NFR-SEC-002

Tokenの有効期限を管理する。

## NFR-SEC-003

Sessionの失効状態を検証する。

## NFR-SEC-004

Logout後に旧Sessionを再利用できないこと。

## NFR-SEC-005

OAuth Providerから取得したCredentialを安全に扱う。

## NFR-SEC-006

OAuth ProviderのSecret、JWT Secret、Internal Token等の機密情報をソースコードへ直接記述しない。

## NFR-SEC-007

高リスクログインに対して追加認証を要求できること。

***

# 12. 現行実装との差異・課題

以下については、要件としては必要だが、現行実装では完全なTraceabilityが確認できていないため、今後の設計・実装確認対象とする。

### GAP-AUTH-001

Logout処理とSession Revocationの完全な接続を確認する必要がある。

### GAP-AUTH-002

Refresh Tokenについて、Session検証、Revocation、Rotationを含む完全なLifecycleを確認する必要がある。

### GAP-AUTH-003

Session生成処理とSession Persistenceの接続を確認する必要がある。

### GAP-AUTH-004

OAuth Email Merge時のEmail Verified条件を明確化する必要がある。

### GAP-AUTH-005

GraphQL上で定義されているRoleとDomain上のRoleの差異を整理する必要がある。

### GAP-AUTH-006

Access Tokenの有効期限について、複数実装間で統一された設定値を確認する必要がある。

***

# 13. 要件の完了条件

本機能は、以下を満たした場合に要件を満たしたものとする。

1. OAuthによってUserを安全に認証できる。
2. OAuth IdentityをUserに正しく関連付けられる。
3. 新規UserがCUSTOMERとして作成される。
4. User Roleに基づく認可が機能する。
5. Account Statusによって利用可否を制御できる。
6. 認証成功後に有効なSessionが生成される。
7. Access TokenとRefresh Tokenを適切に区別できる。
8. Sessionが無効化された場合、旧Tokenによるアクセスを拒否できる。
9. LogoutによってSessionを無効化できる。
10. 高リスク認証に対してChallenge / OTPを要求できる。
11. 権限昇格を防止できる。
12. User、OAuth Identity、Session、Roleの責務が明確に分離されている。

# 22. 現在の重要Gap

## GAP-BR-001：LogoutのSession識別

現在のLogout Resolverでは、SessionをRevokeする処理にUser IDが渡されている。

一方、Session Serviceの`revokeSession()`はSession IDを対象とする設計となっている。

したがって、

```text
Current User
     ↓
User ID
     ↓
revokeSession()
     ↓
？？ Session ID
```

という責務上の断絶が存在する。

**必要対応：**

```text
JWT
 ↓
sessionId
 ↓
logout
 ↓
revoke(sessionId)
 ↓
AuthGuard
 ↓
DENY
```

とする。

---

## GAP-BR-002：Session生成と永続化

`SessionService.createSession()`ではJWT発行処理が存在する一方、AuthGuardではSession Repository / ModelによるSession存在確認を要求する。

したがって、

```text
Login
 ↓
createSession()
 ↓
JWT発行
 ↓
Session DB保存？
```

の永続化経路を明確化する必要がある。

---

## GAP-BR-003：Refresh Token Lifecycle

Refresh Token RepositoryおよびSession Repositoryには必要なインフラ機能が存在するが、現行`refreshToken` ResolverではSession状態確認・Rotation・旧Refresh Token無効化までの一連の処理が完全には接続されていない。

したがって、Refresh Token Lifecycleは🟡とする。

---

## GAP-BR-004：Email Verification

OAuth Profileには`emailVerified`が存在するが、Emailによる既存User連携条件として明示的に利用されていない。

Account Linkingの業務ルールとして、

```text
OAuth Email
   ↓
emailVerified == true ?
   ↓
既存User検索
   ↓
Identity Linking
```

という条件を明確化する必要がある。

---

## GAP-BR-005：Global RoleとTenant Roleの境界

現在Global Roleには、

```text

CUSTOMER
STAFF
MODERATOR
HOST
AGENT
OWNER
ADMIN
SUPER_ADMIN
```

が定義されている。

一方、Tenant Membershipでは別のRole体系を持つ。

したがって、Block 2では、

```text

    ≠
Tenant Membership Role
```

を明確に定義する必要がある。

---

## GAP-BR-006：GraphQL ContractとDomain Contract

GraphQL側では`TENANT_ADMIN`およびApple / LINE Providerが定義されている一方、現行Domain側のRole / OAuthProviderTypeでは同一範囲が定義されていない。

# 18. 状態機械上の重要な設計原則

Block 1では、以下を設計原則とする。

### 原則 1：Authentication StateとAccount Stateを分離する

```text
Authentication State
    ≠
Account Status
```

例えば、

```text
User Account = ACTIVE
Session       = REVOKED
```

という状態は成立する。

したがって、UserのAccount StatusとSessionのAuthentication Stateを一つのStateとして扱わない。

---

### 原則 2：Role StateとSession Stateを分離する

例えば、

```text
User Role    = HOST
Session      = ACTIVE
```

または、

```text
User Role    = HOST
Session      = REVOKED
```

はいずれも成立する。

Role変更とSession Lifecycleは別の責務として管理する。

---

### 原則 3：UseCaseは状態遷移をオーケストレーションする

UseCaseは単一Entityの内部Ruleを再実装せず、

```text
OAuthLoginUseCase
      ↓
Identity
      ↓
User
      ↓
Risk
      ↓
Session
```

のように複数Domain Objectを組み合わせて業務フローを完成させる。

---

### 原則 4：Domain Entityは自身の不変条件を守る

例えばHost昇格の場合、

```text
BecomeHostUseCase
       ↓
UserEntity.becomeHost()
```

とし、

```text
ADMIN
SUPER_ADMIN
```

のHost昇格禁止RuleをDomain Entity側で保証する。

REQ-TROLE-004
系统应通过 Permission Matrix 定义业务操作权限，
而非直接以 Role 作为业务权限定义。

BR-PERM-001
Permission 采用 Resource + Action 模型。

BR-PERM-002
Authorization 必须考虑 Scope。

BR-PERM-003
SELF Scope 必须结合 Resource Ownership 判断。

BR-PERM-004
TENANT Scope 必须结合 Active Tenant 判断。

BR-PERM-005
Tenant-scoped authorization 必须结合 Membership 判断。

BR-PERM-006
GLOBAL Scope 用于平台级管理操作。

BR-PERM-007
Role 是 Permission 的集合，而不是 Permission 本身。

BR-PERM-008
Global Role 与 Tenant Membership Role 应作为不同维度处理。


| Role            | Scope             | Ownership   | 典型权限               |
| --------------- | ----------------- | ----------- | ------------------ |
| **CUSTOMER**    | Tenant / Resource | 通常自己的订单     | 创建订单、查看自己的 Booking |
